# Run the student-simulation prototype

**TL;DR:** Install the workspace dependency, create the fictional offline demo,
and open its saved tutor-policy comparison. No student data, API key, database or
Docker is needed for this first walkthrough. Private sessions and live Gemini
generation are separate, optional steps below.

## 1. Set up the checkout

Use macOS, Linux, or Windows through WSL; session locking currently requires
POSIX. Install [uv](https://docs.astral.sh/uv/getting-started/installation/) if
needed. Run every command below from the repository root containing
`pyproject.toml`, `src/` and `apps/`.

These tools are currently on `codex/teammate-quickstart`, pending the PR stack's
normal review and merge. A fresh checkout can use:

```sh
git clone --branch codex/teammate-quickstart https://github.com/dstl-lab/chatsight-summer.git
cd chatsight-summer
uv sync --locked --extra workspace
```

The project requires Python 3.11 or later; the local verification environment
uses Python 3.13.9 and Marimo 0.24.2. Keep the checked-in `uv.lock`. Once this work
is merged, use the team's agreed revision containing it rather than assuming an
older `main` includes these commands.

## 2. Reproduce a saved interaction offline

```sh
.venv/bin/python -m src.agents.chat_demo data/teammate-demo
.venv/bin/marimo run apps/chat_policy_comparison.py \
  --host 127.0.0.1 --port 8425 --headless -- \
  --comparison data/teammate-demo/comparison
```

Open **http://127.0.0.1:8425/**. Both conditions start from the same fictional
conversation and scripted first student reply, then use different fixed tutor
policies. Open **Saved results** to see each tutor reply and student outcome:

- **A:** the student replies, then the fixed decision budget is exhausted.
- **B:** the student explicitly stops without another reply.

These outcomes are authored in advance, not generated by a model. They demonstrate
saving, replay and the distinction between a budget pause and no reply; they are
not evidence about student behavior or which policy works. In this demo only,
the existing **Recorded** label means the fictional seeded conversation context;
**Simulated** replies are scripted fixture values. The saved model identifier is
`authored-offline-demo`, not a Gemini model.

**Reload saved comparison** reopens the same results without generating anything.
The demo creator refuses an existing destination; reopening uses the second
command only. To create another fixture, choose a new destination rather than
deleting or editing the saved one. Stop the server with Ctrl+C.

To inspect the same completed branches one at a time in the generic workspace:

```sh
.venv/bin/marimo run apps/student_workspace.py \
  --host 127.0.0.1 --port 8426 --headless -- \
  --chat-sessions data/teammate-demo/comparison/sessions
```

Open **http://127.0.0.1:8426/** and select `a` or `b`. Both are finished and
viewing only. The Notebook tab correctly shows that notebook activity is unknown.

## 3. Open private working sessions, when provided

The real course scenarios are not in Git. Obtain a private bundle from the team
containing complete session directories, together with its exact code revision
and `uv.lock`. Agree on that revision before transferring the bundle and check
out the matching revision before opening it. Saved sessions verify their source
and schema; do not change their hashes or receipts to make a mismatch disappear.

Use separate working copies under ignored `data/workspace/sessions/`, with one
subdirectory per scenario. Preserve every file in each session, including its
manifest, student steps and any tutor exchanges. Keep the original frozen
research files separate and unchanged. For policy comparisons, transfer the
whole comparison directory, including `comparison.json` and both child sessions.

```sh
.venv/bin/marimo run apps/student_workspace.py \
  --host 127.0.0.1 --port 8426 --headless -- \
  --chat-sessions data/workspace/sessions
```

Select a scenario and inspect **Conversation** and **Saved results**. Viewing
requires no credentials, tunnel, database or Docker. Chat scenarios expose the
conversation only; code in a message does not establish notebook work or a run.

## 4. Optionally continue a live session

For a supplied working session with a real Gemini model and remaining decisions,
set `GEMINI_API_KEY` in the environment or a local repository-root `.env` file.
Use `.env.example` for the variable name; no database password is needed here.
Stop the viewing server and relaunch with the explicit sending option:

```sh
.venv/bin/marimo run apps/student_workspace.py \
  --host 127.0.0.1 --port 8426 --headless -- \
  --chat-sessions data/workspace/sessions --send=true
```

Choose **Tutor policy** to request one tutor reply and then one student decision,
or **Write a reply** to supply the tutor message and request only the student.
Click the continuation button once; the two model requests run sequentially and
may take tens of seconds. Inspect the new conversation above the controls and its
Saved results entry. Reloading never requests another reply. Drafts reset when
switching scenarios and are not saved across a server restart.

Bare `--send` does not enable these Marimo controls; use `--send=true` after `--`.
Do not enable live generation for the scripted demo. Failed or interrupted
requests remain saved and cannot be resent automatically; inspect their results
instead of editing receipts or extending an exhausted budget. Keep session data
and credentials out of Git. This prototype supports inspection and intervention;
realistic student behavior and learning effects remain unvalidated.
